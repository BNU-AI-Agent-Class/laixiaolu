# 反思：哪一步最像 / 最不像真 Claude Code？

## 最像真 Claude Code 的一步

**定位根因的过程最像真 Claude Code**：先跑命令复现报错，再直接读取 `analyze.py`，根据Traceback 里的行号锁定 `counts[0][0]`，并说出“空列表导致越界”的原因。这和真 Claude Code 的调试节奏一致——报错 → 读源码 → 解释原因 → 最小改动修复，而不是一上来就盲改。

## 最不像真 Claude Code 的一步

**“修复后手动验证”这一步最不像真 Claude Code**。真 Claude Code 在改完代码后通常会主动运行测试或相关命令来验证，并且能利用 `Read`/`Grep`/`Glob` 等结构化工具做交叉检查；而 `c5_guard.py` 这类 mini 版只有 `bash` 一个工具，所有文件读取、搜索、编辑都要靠模型自己拼 shell 命令，既没有专门的文件工具，也没有自动化的验证闭环，容易漏掉“恢复原始数据再测一遍”这类步骤。

## 还差哪个机制？

我觉得 mini 版还差两个关键机制：

1. **结构化文件工具**：真 Claude Code 有 `Read`/`Edit`/`Grep`/`Glob`，能精准读写、搜索，而 mini 版只有 `bash`，读文件要靠 `cat`、改文件要靠 `sed/echo`，既容易出错又难以处理编码和长输出。
2. **自动验证 / 计划闭环**：真 Claude Code 在动手前会先列计划，改完会自动跑命令验证；mini 版则是单轮对话循环，需要用户不断催促“验证一下”“恢复数据再测”，缺乏“计划 → 执行 → 验证 → 报告”的自治流程。
